# Page-first publication implementation plan

## Status and purpose

Status: implemented for the first milestone. Paged.js `0.5.0-beta.2` is the
selected backend, pinned and recorded in
[PAGEDJS_FEASIBILITY.md](PAGEDJS_FEASIBILITY.md). The desktop preview, CLI
worker, and MCP job paths share one revision-bound paginated artifact; the
flowing HTML profile remains available for HTML export.

Delivered in this milestone:

- Shared physical/logical page plan with cover slots, legacy first-page modes,
  and an opt-in body restart after the contents.
- Typed `\clearpage` and `\pagetemplate{...}` layout controls that ignore
  literal contexts.
- Isolated Paged.js layout with repeat table headers, bounded contents-reference
  convergence, shared folios, and whole-sheet template backgrounds.
- Static page preview with page count and navigation, revision-bound pagination
  summaries, and an integrated `restartBodyAfterToc` control.
- PDF printing from the finalized artifact with zero page margins, cover
  placement before generated pages, and preserved link destinations.
- `scripts/check-page-first-publication.mjs`, an end-to-end acceptance check
  covering all seven acceptance points through the production CLI worker.

Deferred: recto starts, explicit blank pages, Roman front matter, background
images and watermarks, page virtualization, spreads and thumbnails, arbitrary
page editing, and template authoring beyond the built-in `default`, `toc`, and
`section` templates.

This plan supports the target product and architecture in [SPEC.md](../SPEC.md).
[RENDERING.md](RENDERING.md) documents the existing continuous-preview and
print-time-pagination implementation, not the completed upgrade.

The goal is a page-oriented publication system, not merely a preview that looks
like separate sheets. The first milestone must deliver these capabilities
together:

- Whole-page backgrounds, including the margin area, with section-scoped page
  templates.
- Publication page numbers visible in preview and generated by the same page
  rendering path as PDF output.
- A table of contents with correct logical page references after reflow.
- Explicit page-ending controls, including a standalone `\clearpage` directive.

Markdown and versioned publication configuration remain the editable source of
truth. Generated pages are revision-bound build artifacts, not a new manuscript
format or independently editable page files.

## Scope and non-goals

The first release includes portrait A4 and Letter, automatic prose pagination,
explicit breaks, page-template backgrounds, shared folios, numbered contents,
page navigation, source-linked layout diagnostics, and the existing Markdown
features. GUI, CLI, and MCP must use the same publication pipeline.

Do not require multi-source project support to deliver this milestone. Preserve
the current single-source workflow and leave room for additional publication
parts through the document model.

Deferred capabilities include freeform page editing, WYSIWYG authoring,
arbitrary floating figures, advanced running headers, footnotes, multicolumn
body layout, complex feature-page composition, incremental reflow, and
commercial prepress. Preserve existing approved theme-background assets; new
user-configurable image and watermark controls are deferred. The contracts
should accommodate future recto starts, explicit blank pages, Roman-numbered
front matter, background images, and watermarks without claiming that all of
them ship in the first release. Page virtualization is a separate performance
decision, not a prerequisite for real pagination.

## Current implementation and reference assessment

The existing boundaries are useful and should be retained:

- `packages/publication-core/src/markdown.ts` compiles Markdown with Shiki,
  KaTeX, sanitization, embedded assets, and deterministic heading anchors.
- `packages/publication-core/src/model.ts` represents compiled chapters and TOC
  entries, but has no complete page plan or explicit layout-control nodes.
- `packages/publication-core/src/html.ts` produces flow-based HTML with `@page`
  and print fragmentation rules.
- `apps/desktop/src/renderer/app/preview-canvas.tsx` displays a paper-width
  iframe whose height grows with its content.
- `apps/desktop/src/main/services/publication-service.ts` shares compilation
  between entry points and orchestrates printing and PDF assembly.
- `electron-print-backend.ts` waits for publication resources before Chromium
  pagination; `page-number-pdf-service.ts` stamps folios afterward.
- `pdf-assembly-service.ts` adds image or imported PDF covers after body
  printing.

[Frontend Textbooks](https://github.com/onepixelaway/frontend-textbooks)
provides the inspiration: explicit sheets, measured overflow, source identities,
page furniture, and verification before PDF delivery. Its
[browser paginator](https://github.com/onepixelaway/frontend-textbooks/blob/main/scripts/lib/book-client-program.mjs)
mostly moves complete blocks between fixed-size pages and rejects blocks that
cannot fit on one page. That is not sufficient for general long paragraphs, code
blocks, lists, and tables. Reuse the architectural ideas rather than its
block-packing algorithm, mandatory artwork workflow, or content-preservation
threshold. Supported manuscript content must not be silently lost or abridged.

## Architecture decisions

### Shared page-oriented pipeline

```text
Markdown + publication configuration + captured assets
  -> parsing, normalization, semantic nodes, and source identities
  -> sanitized semantic HTML, theme, resolved fonts/images/math/diagrams
  -> publication parts + page templates + layout controls
  -> isolated layout backend
  -> initial PagePlan
  -> logical numbering + TOC/reference resolution
  -> bounded reflow until page assignments and references stabilize
  -> finalized PaginatedPublication
       -> static desktop page preview
       -> Chromium PDF for generated pages
            -> imported-page assembly and metadata
            -> final verification and atomic write
```

The existing flowing, body-only HTML export branches from the semantic HTML
stage. Do not silently replace its behavior with fixed sheets. A paginated HTML
profile can be added later through an explicit, versioned contract.

Chromium remains the PDF renderer, but it must not independently choose new body
breakpoints after the shared layout has been finalized. Preview and export use
the same artifact revision, layout CSS, assets, and generated page content.
Print-only rules may remove viewer chrome, shadows, and gaps; they must not
change typography or content geometry.

### Logical contracts

Names below describe responsibilities, not finalized public TypeScript or YAML
schemas:

| Contract                          | Responsibility                                                                                                                       |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| `PublicationDocument`             | Ordered parts, source-linked flow blocks, generated contents, imported-page slots, explicit page content, and typed layout controls. |
| `PageTemplate` / `PageLayoutSpec` | Physical dimensions, content bounds, reserved header/footer regions, background layers, and template scope.                          |
| `PagePlan`                        | Complete ordered page sequence, page kinds, applied templates, numbering policies, and imported/generated origin.                    |
| `PageMap`                         | Heading and source-fragment locations within a particular page-plan revision.                                                        |
| `PaginatedPublication`            | Finalized static page HTML/CSS, page plan, source map, resource identity, diagnostics, and build/runtime identity.                   |
| `LayoutBackend`                   | Replaceable browser-dependent layout implementation behind the application-owned contracts.                                          |

Use stable source-block and heading identities, with source ranges carried
through preprocessing, sanitization, math, and Mermaid replacement. A block may
produce multiple page fragments. Generated page IDs are scoped to a layout
revision; do not treat page indices as stable manuscript identities.

Keep semantic contracts and transforms in publication core, validated
browser-safe request/result contracts in shared, and runtime/path safety in
publishing runtime. Main owns layout-window lifecycle, artifact caching,
printing, and assembly. React presents results and interactions rather than
implementing a second paginator. Add a package only if real consumers justify
that boundary.

### Page templates and backgrounds

A generated page has distinct background, header, content, and footer layers.
Backgrounds cover the physical sheet, including margins, without contributing to
prose flow. Reserve furniture space before laying out body content.

Template rules should primarily target publication parts, page kinds, or source
anchors, not absolute physical page numbers that change after reflow. A template
switch at a content boundary starts a new page by default. Do not assign two
conflicting whole-page templates to sections sharing one sheet. Local paragraph
or code backgrounds remain content styles.

Normalize legacy theme rules for `body`, `.chapter`, screen/print media, and
page margins into the page-content context. Use one physical margin model; do
not combine full-sheet padding with a second set of printer margins. Whole-page
color changes may eventually reuse measured geometry, but geometry-changing
style updates must trigger reflow. Correctness takes priority over this cache
optimization.

### Physical pages, logical labels, and folios

Resolve numbering from the complete page sequence, including known imported
cover slots and any intentionally inserted blanks. Keep these concepts separate:

- Physical page position in the final PDF.
- Numbering group and logical label, such as `1` or a future `iv`.
- Whether a label is displayed on the page.
- Footer text, such as `3 / 20`, rather than the bare label used in a TOC.
- The total-page scope used by each numbering policy.

Preserve existing defaults and all three first-page modes: covers are unnumbered
and outside the legacy body total; a generated TOC belongs to that body total.
Hiding the first folio and restarting on the second must retain its existing
effect on `{page}` and `{pages}`. Add an explicit opt-in policy for restarting
at the main body after the TOC, used by the acceptance scenario below. Reserve
more general per-part numbering and Roman labels for later work.

Render finalized folios through the shared page HTML for both preview and PDF.
Preserve bundled Latin font selection, supported styles, 6–24pt sizing,
printable ASCII format validation, and missing-glyph diagnostics. Revalidate
font embedding, output size, and raster correctness when changing the rendering
path; the existing PDF stamping tests are migration requirements, not disposable
code.

The current PDF folio service may remain as a temporary legacy-path backend.
Never stamp a second folio onto pages that already contain shared HTML folios.
Do not claim exact preview/PDF parity while two independent furniture renderers
remain in the active page-first path.

### TOC and cross-reference convergence

Keep deterministic heading anchors. Resolve each TOC destination to its final
logical label, not its physical index plus an assumed cover offset. Repeated
headers, cloned table headings, hidden source trees, and continuation fragments
must not create false destinations.

Create a real, potentially multipage TOC before pagination. Reserve a
predictable page-label column, lay out the document, resolve heading labels,
refill the TOC, and reflow when that changes geometry. Stop only when page
assignments and resolved references stabilize. Use a bounded iteration policy
and cycle detection; report an actionable convergence failure rather than
shipping stale references. Do not assume that two passes always suffice.

The same mechanism can later serve figure/table lists and page cross-references;
those authoring features are not required for this milestone. Verify clickable
TOC destinations both before and after imported-page PDF assembly.

### Explicit layout controls

Parse layout instructions into typed nodes before rendering instead of using
global string replacement or relying on empty HTML elements surviving print
fragmentation.

| Control         | Semantics                                                                                                 |
| --------------- | --------------------------------------------------------------------------------------------------------- |
| Page break      | Start subsequent content on a new page.                                                                   |
| Clear page      | End the current page and start subsequent content on a new page; reserve a future float-draining barrier. |
| Recto start     | Start on the next eligible right-hand page, inserting a planned blank if needed; deferred.                |
| Blank page      | Insert an intentional physical page with explicit template and numbering rules; deferred.                 |
| Template switch | Apply a new page template at a new-page boundary.                                                         |

Support standalone `\clearpage` outside fenced/indented code, inline code, math,
raw HTML blocks, and other literal contexts. It is a documented Markdown layout
extension, not a general TeX interpreter. Without a floating-content queue,
clear page means a forced page ending; do not claim full LaTeX float-flushing
behavior. Do not emit accidental empty pages for leading, trailing, or
consecutive break controls. A deliberate blank page must be an explicit semantic
operation.

Treat directive markers as non-reader-facing controls. Preserve source ranges
for diagnostics. Define a safe, documented treatment for the existing flowing
HTML profile during implementation; it must never leak the raw directive as
reader-facing text or silently acquire fixed-page semantics.

### Fragmentation and content integrity

Use the browser layout backend to split prose while preserving semantic order.
At a minimum:

- Keep headings with a useful amount of following content and control widows and
  orphans.
- Split lists with correct numbering and nesting.
- Keep short code blocks together; split long code by lines with syntax colors
  and source order preserved.
- Split tables by rows and repeat headers. Diagnose overheight rows and widths
  that cannot be made printable without unacceptable loss.
- Keep figures, Mermaid diagrams, and display math together where possible.
  Apply a documented fit policy or report an actionable oversized-item error.
- Preserve image aspect ratios, link destinations, and unique semantic anchors.

Do not hide errors with `overflow: hidden`, shrink arbitrary content into
illegibility, rasterize the body, or accept a percentage-based content-loss
threshold. Distinguish unsupported source features and compilation warnings from
content lost during pagination.

### Isolation, readiness, and artifact lifecycle

Run only application-owned bundled layout code in a main-controlled sandboxed
publication window. Continue rejecting source JavaScript, event handlers,
unapproved assets, navigation, and remote requests. Keep the desktop preview
static and script-disabled; do not solve integration by combining
`allow-scripts` with its existing `allow-same-origin` sandbox permission.

The backend evaluation must prove compatibility with the publication CSP,
stylesheet generation, approved data assets, and the trusted execution boundary.
Validate generated artifacts without blindly applying a source sanitizer that
would remove required engine-generated layout structure.

Readiness includes fonts actually used by the content and folios, loaded images,
finished math/diagrams, completed layout, converged references, and geometry
checks. Use explicit signals and bounded deadlines, not fixed sleeps. Support
cancellation, resource cleanup, bounded concurrency, and superseded requests.

Bind artifacts to captured source/configuration/asset bytes plus theme, font,
layout-engine, and Chromium identities. Export a requested valid revision or
explicitly reject/rebuild an outdated result; never silently print different
content behind an unchanged preview. Do not duplicate font assets per page.

Imported PDF covers remain vector pages in the final assembly, although preview
may use controlled raster representations. Plan their slots before numbering,
omit them from generated HTML printing, and insert them exactly once. Verify
both generated-page counts and complete assembled-page counts. Visual parity
means matching layout, labels, backgrounds, and destinations, not an unmeasured
claim of pixel-identical rasterization.

## Backend evaluation

| Candidate                                  | Assessment                                                                                                                                                    |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Paged.js behind an adapter                 | First candidate. Browser pagination and extension hooks fit the existing stack; MIT licensing fits the current distribution model. Must pass actual fixtures. |
| Vivliostyle Core                           | Alternative if needed. Evaluate API/runtime cost and AGPL-3.0 obligations before selecting or distributing it.                                                |
| Complete-block custom paginator            | Not a general default: oversized prose/code/tables require substantial fragmentation work.                                                                    |
| Decorative page lines or clipped viewports | Reject: they do not establish a shared page model or reliable page references.                                                                                |

Pin an evaluated published version and record its actual API, limitations,
license, transitive dependencies, and bundle impact. Do not assume the current
repository branch matches an npm release. Do not add a second browser or adopt
an engine merely because its demo renders separate sheets. Reconsider selection
if basic fixtures require extensive changes to engine internals.

## Implementation phases and gates

### P0: End-to-end feasibility slice

After separate authorization, evaluate the candidate backend with actual project
themes, resource readiness, and sandbox restrictions. Build the seven-point
acceptance scenario below rather than only demonstrating blank sheets and prose.
Also include representative CJK, long code, tables, KaTeX, Mermaid, and images
so the slice cannot pass by avoiding existing content support.

Prove that static pages survive transfer to the script-disabled preview and
printing without changed breakpoints. Measure layout time, memory,
responsiveness, and cancellation for small, medium, and long publications on a
recorded reference machine. Document observed results and choose performance
budgets from evidence.

Exit gate: the four requested capabilities work together, generated/assembled
page counts agree, content is preserved, the security boundary holds, and there
is a credible path for difficult blocks. Otherwise revise the backend decision
before broad implementation.

### P1: Domain model, configuration, and theme boundaries

Define the logical contracts, numbering policy, source mappings, directive
parser, template scopes, and safe serialization. Normalize theme geometry. Keep
existing schemas and defaults backward compatible; introduce versioned
configuration/capabilities rather than passing unknown fields into strict v1
contracts. Finalize any additional template-selection syntax here, with tests.

Exit gate: focused unit tests cover numbering compatibility, source identity,
literal-context exclusions, template boundaries, and explicit-break edge cases.

### P2: Production layout and reference resolution

Integrate the chosen backend behind the application interface. Implement
resource readiness, block-fragmentation policies, shared folios, complete page
plans, TOC convergence, diagnostics, artifact identity, cancellation, and
cleanup.

Exit gate: targeted browser integration fixtures pass without missing text,
unexplained empty pages, unresolved references, or out-of-bounds content.

### P3: Desktop and MCP page presentation

Replace the continuous canvas with static fixed-size pages. Add page position,
count, and jump controls while preserving fit width, 25–200% manual zoom, actual
size, draft-style behavior, and application/publication appearance separation.
Zoom must not recompile or reflow. Restore reading position through source
anchors after reflow and distinguish pending, ready, failed, and stale results.

Extend revision-bound MCP snapshots, navigation, and captures through validated
capabilities while retaining existing heading/scroll operations where
applicable. Keep the contract focused on pages; do not expose arbitrary DOM or
script tools. Thumbnails, spreads, and virtualization can follow measured need.

Exit gate: GUI and MCP observe the same page revision and cannot export or
capture a silently superseded layout.

### P4: PDF integration, compatibility, and rollout

Print the finalized generated pages with no independent content reflow or
duplicate folios. Assemble planned imported pages, preserve vectors, verify
dimensions and internal links, and write atomically. Route desktop, CLI workers,
and MCP file jobs through the same service. Preserve flowing HTML behavior and
legacy configuration while documenting opt-in numbering/template additions.

Use a migration switch for the complete layout/preview/export path. Never
combine new paginated preview with old independently paginated PDF output or
silently fall back after a page-first layout error.

Exit gate: all entry points agree on the same inputs, numbered TOC, breakpoints,
page sequence, labels, and diagnostics. Update implementation-facing rendering,
security, CLI, MCP, and skill documentation when those behaviors actually
change.

### P5: Regression hardening and default transition

Exercise every built-in theme and both paper sizes using structural assertions
and focused screenshots. Validate packaged Electron behavior on supported
desktop platforms, offline asset handling, malicious inputs, repeated jobs, and
cancellation. Record known limitations and compare performance to P0 budgets.

Switch the default only after the complete acceptance scenario and relevant
regression gates pass. Remove legacy code separately after compatibility is
proven, not as an incidental cleanup during this upgrade.

## Acceptance scenario

One reproducible publication must demonstrate all of the following together:

1. An unnumbered front cover occupies its correct physical position.
2. A multipage TOC uses its own whole-sheet background and correct logical page
   references.
3. Main-body numbering can explicitly restart at 1 after the TOC, and its real
   folios are visible in preview and PDF.
4. A selected section begins on a new page with a different page template and
   background, including the margin area.
5. A standalone `\clearpage` ends the same page in preview and PDF, without
   interpreting occurrences in code and math as page controls.
6. Changing body typography updates pagination, TOC references, and scoped
   totals together without stale page labels.
7. Final PDF page order, dimensions, folios, backgrounds, and clickable TOC
   destinations agree with the finalized preview artifact, including after cover
   assembly.

## Validation strategy

- Unit tests: numbering groups and legacy modes, layout controls,
  source-fragment identity, template precedence, configuration migration, and
  convergence logic.
- Chromium integration: fonts/images/diagrams, long-block fragmentation, static
  artifact transfer, backgrounds, folios, TOC wrapping, and overflow detection.
- PDF checks: expected generated and assembled page counts, dimensions, text
  presence and order, folio glyphs, links, backgrounds, and representative
  raster comparisons. Account explicitly for repeated table headers and
  generated furniture; unordered word presence alone does not prove
  preservation.
- Desktop/MCP/CLI checks: revision handling, navigation, stale-result rejection,
  export equivalence, cancellation, and packaged resource paths.
- Security/performance checks: CSP, script-disabled preview, asset boundaries,
  malicious source/CSS, bounded iteration, memory cleanup, and measured
  workloads.

Use pnpm and existing tooling. Run relevant targeted tests for each
implementation change, not the entire suite by default. Add production build
checks when bundles, trusted runtime loading, preload, startup, or packaging
change. For this planning-only change, check formatting, links, and the diff; no
runtime validation or backend performance claim is implied.

## Risks and outstanding decisions

- Backend compatibility and serialized-page fidelity remain unproven until P0.
- Complex table rows, oversized diagrams, and long code are likely integration
  hotspots; define fit/failure behavior instead of hiding loss.
- TOC growth can feed back into pagination; bounded convergence is mandatory.
- Theme selectors and competing margin models can invalidate measured geometry.
- Folio migration must preserve font rendering and existing numbering defaults.
- Additional template authoring syntax, new configuration versions, convergence
  limits, and performance budgets must be finalized with evidence before being
  exposed as public contracts. The first release fixes the engine at
  `0.5.0-beta.2`, uses a three-pass convergence limit, and documents measured
  layout times rather than promising fixed budgets.

Indicative effort from the assessment: 2–4 person-days for feasibility, roughly
3–5 person-weeks cumulatively for a usable first version, and 5–8 person-weeks
cumulatively for complex-content and cross-platform hardening. These are not
commitments. Remaining hardening is tracked above as deferred work rather than
as unstarted phases.
